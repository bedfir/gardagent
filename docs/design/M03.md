# M03: Versioned migrations

## Problem

Startup replays all DDL, including ledger trigger replacement. There is no durable schema version or protection against simultaneous migration and downgrade.

## Decision

Use a dedicated pooled connection and a session advisory lock for the entire migration sequence. Each numbered migration and its version record commit in one transaction. Bootstrap of the version table is transactional too. Validate contiguous recorded versions and refuse versions newer than this executable. Release the lock before returning the connection; destroy the connection if unlock fails.

Migration 1 creates the 0.3.0 schema on an empty database. For an unversioned database containing application tables, validate the complete expected column set, indexes and enabled append-only trigger before recording adoption; execute no application DDL and touch no existing rows. Partial older schemas require restoration or an explicit future upgrade path, rather than guessed repairs. Versioned restarts read only migration metadata.

Keep the original 0.3.0 SQL as an independent test fixture. Production initial DDL lives in the migrations module. Do not change ledger serialization, spend, reservation semantics or the in-memory store (which has no persistent schema).

## Alternatives rejected

Replaying IF NOT EXISTS DDL still takes table locks and replaces the trigger. One transaction for the entire history would erase successful earlier migrations on a later failure. Concurrent index builds cannot participate in the required migration transaction.

## Compatibility impact

Complete 0.3.0 installations are adopted without application DDL. Incomplete/unrecognized unversioned schemas and future versions fail before listening. No automatic downgrade: restore a backup with the corresponding executable. No claims about elapsed time without a new runner measurement.
