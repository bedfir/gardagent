# M06 — Ledger export and external checkpoints

Problem: list and CSV output do not capture a head, and internal integrity alone cannot detect a valid shortened or replaced chain.

Decision: both stores expose an atomic head read. GET export.ndjson returns ascending sequence pages bounded by a captured head, with a metadata line carrying the checkpoint and next cursor. Continuations carry the original sequence and hash; a changed or missing anchor is rejected. Append-only storage makes a fixed upper bound sufficient under concurrent appends without holding a transaction across requests. GET checkpoint returns a versioned external anchor. POST verify accepts that anchor, verifies the current captured chain, and reports checkpoint membership. Existing GET verify remains supported. Verification explicitly checks sequence continuity across page boundaries and the captured terminal hash.

Alternatives rejected: offset pagination can drift; unbounded verification can chase writers; long-lived snapshots retain database resources across client requests. This protocol promises consistency under appends, not privileged mutation during a request.

Compatibility: no schema or ledger hash changes, including legacy entries. The checkpoint envelope format is gardagent-checkpoint-v1 and is separate from entry format versions. Empty ledgers use sequence zero and the genesis hash. Only a checkpoint retained outside the database detects truncation or replacement relative to that checkpoint; rewriting history after the anchor is not detected by that anchor alone.
