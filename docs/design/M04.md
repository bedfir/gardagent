# M04 — Versioned ledger format

Problem: new revision, operator and approval references must be authenticated without changing historical hashes.

Decision: keep canonical JSON and hashing unchanged. Store writers stamp every new entry with version 2; the low-level
chain constructor remains usable for historical fixtures. Add nullable columns with no defaults in migration 2 and
omit null columns when rebuilding entries. Verification checks sequence, link, supported version, hash, then generic
content rules and the non-decreasing version boundary. This preserves hash-mismatch diagnostics for tampering.

Approval semantics belong to the gateway and M05, which supplies those references; core checks only generic format
constraints. Document that implementation boundary explicitly. Verification returns the last verified format version
and accepts it as continuation state. The full-chain admin endpoint carries this state across every page, so a
version regression cannot hide at a page boundary. Independent ranges default to version 1. Empty pages preserve
the supplied state. Undefined optional fields are absent, consistently with canonical JSON hashing.

Rejected: backfilling version 1, changing canonicalization, or stamping entries while reading. Each would invalidate
old proofs. Reject silently accepting explicit version 1: the only historical marker is absence.

Compatibility: historical entries and golden files remain untouched. New API ledger entries gain an additive marker;
contract shape assertions must allow this documented addition. Successful core verification results also gain
`lastVersion`; golden-result assertions retain exact hash checks and assert version 1. The admin HTTP response
shape stays unchanged. No dependencies. Runner executes all checks.
