# M02: Initial contracts

Problem: M03–M10 each change a surface that outside parties depend on (database schema, ledger entries, HTTP API, MCP
traffic, the mandate). Without a written contract first, each mission would define it by what it happens to implement.

Decision: documentation and golden fixtures only, no behaviour change.

- `docs/ledger-format.md` describes the 0.3.0 format from the code as format version 1, then specifies version 2. The
  single rule that keeps version 1 verifiable: the hash input is every present field except `hash`, one algorithm for
  all versions, no backfill, and new fields (including the `formatVersion` marker) are absent unless they have a value.
  An unmarked entry is version 1.
- `docs/mandate.md`: named operator tokens stored hashed, the bootstrap operator, policy revisions identified by the
  hash of their canonical form, approvals correlated to the entry they authorize by `approvalRef`.
- `docs/mcp-matrix.md`: an allow-list matrix; everything not listed is refused.
- `docs/compatibility.md`: what is stable, what compatible means, the deprecation rule, what is not covered.
- Golden fixtures in `test/fixtures/contracts/`, generated by `apps/gateway/test/contracts.test.ts` from the real routes
  on the in-memory store, and a contract test that verifies them with the current code and with an independent
  implementation of the documented algorithm.

Alternatives rejected:

- Fixtures typed by hand: they could disagree with the code. Generated ones cannot.
- A default `degraded: false` or `formatVersion: 1` written on old rows: it changes their hash (trap 1). The version of
  an entry is inferred from the marker's absence instead.
- A separate hash function for version 1: two code paths to keep equal. One presence-based rule covers both.
- Regenerating fixtures on every run: the contract would then verify itself. A fixture file that exists is never
  rewritten unless `GARDAGENT_UPDATE_FIXTURES=1`. The only implicit write is the bootstrap: none of the five files
  exists and `CI` is unset.

Compatibility impact: none at runtime. The documents commit later missions to the field names `formatVersion`,
`policyRev`, `operatorId`, `approvalRef`, the operator id `bootstrap`, the token prefix `gaop_`, and the MCP matrix; a
mission that needs to depart from them must change the document in the same change.

Limits: the fixtures were not generated when this was written (the author cannot run the toolchain); the first test run
creates them and they must be committed. The ledger chain proves nothing against tail truncation or a full rewrite
without an external checkpoint, as the format document says.
